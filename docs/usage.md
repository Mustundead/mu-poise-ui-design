# MU LABS Poise · UI 设计使用文档

## 安装

本仓库根目录就是技能目录，内部链接使用相对路径。发行包应保留整个目录，不能只复制 `SKILL.md`。

在 MU LABS 使用的本地 Codex 技能目录中，可执行：

```sh
mkdir -p ~/.codex/skills
git clone https://github.com/Mustundead/mu-poise-ui-design.git ~/.codex/skills/mu-poise-ui-design
```

如果你的助手配置使用其他技能目录，将目标路径替换为那个目录；不要为了安装而更改全局配置或复制凭据。`git clone` 在目标已有内容时会拒绝覆盖。对于 ZIP，先解压、确认目录结构，再放入技能目录。首次安装后开启新会话，检查技能是否已被发现；未出现时核对宿主的目录规则。

这是纯指令技能，不执行安装脚本，不附加 MCP 服务，也不自行联网、上传或发布。

## 如何提问

提供三项足够：要改变的界面/材料、期望结果、希望“评审”还是“直接实现”。语言和平台在会改变工作范围时说明。

```text
使用 $mu-poise-ui-design。调整这个弹层的拖动交互，让它能在回弹途中被重新抓取；保留列表滚动和键盘关闭，验证减少动态效果。
```

实现请求示例：

```text
使用 $mu-poise-ui-design，在当前项目中实现上述修改。
沿用现有设计和术语，只修改这个流程；验证当前运行页面，并说明没有验证到的部分。
```

没有代码、设备或登录也能进行有边界的评审。技能应指出已知事实与假设，不把缺失材料填成产品能力。

## 工作模式

| 模式 | 你会得到什么 | 不会自动发生什么 |
| --- | --- | --- |
| 改写/局部修正 | 对准具体问题的建议或已授权修改 | 全产品重构 |
| 评审 | 有证据的发现、影响与建议 | 自动编辑源文件 |
| 实现 | 源文件修改与受影响结果的验证 | 未授权的发布、交易和数据操作 |
| 审计 | 基于明确范围清单的覆盖情况 | 没有清单的“全产品通过” |

## 与其他技能协作

可以与 MU LABS Phrase 同时使用。让一个负责主要交付，另一个处理必要的文案或交互部分；共享的上下文、构建和运行验收复用一次。不要求必须安装另一项技能。

## 更新、迁移与移除

Git 安装先运行 `git status --short` 检查本地修改，保留自己的定制后再考虑 `git pull --ff-only`。ZIP 安装先比较版本与自己的修改，保存可恢复备份后更换。不要使用 `reset --hard` 来更新技能。

从旧的 `apple-design` 迁移时，先备份旧目录到技能发现目录之外，再安装本技能，避免两个广泛触发的版本同时重复指导。旧名称不会自动重定向；更新自己的调用词为 `$mu-poise-ui-design`。

移除时将本技能目录移出助手的技能发现路径即可。技能不存储账户、项目数据或后台状态。

## 如何理解验证结果

检查 frontmatter 和链接只能证明包结构。真实行为评估见 [evaluation.md](evaluation.md)。一次情境通过不代表所有项目都通过；运行截图不能替代读屏交互，构建不能替代已登录的目标页面，也不表示 App Store 或生产发布。

v1.0.0 的具体发布检查记在发行说明中；后续变更必须重跑受影响部分，不能继承旧的通过结论。
